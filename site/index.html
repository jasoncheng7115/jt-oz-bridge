Talk to your AI coding agent from chat.

jt-oz-bridge connects AI agents with messaging software, starting with OpenCode × Zulip. Type a task in a Zulip topic, watch the agent work, answer its permission requests from your phone and get the complete result, in the same OpenCode session you use at your desk. Everything runs on infrastructure you own.

Source on GitHub Install guide

Status

Development preview 0.1.1 — not a finished production release.

Core routing, persistence and security boundaries have a large automated test suite, and parts of the flow have been observed against a real OpenCode server and Zulip organization. Complete end-to-end use by real people and use on the official iOS/Android apps are not yet verified. Try it on a disposable project first.

What it does

01

AI agents in everyday chat

Tasks, progress, questions and results stay together in your chat, on your phone and your computer.

02

OpenCode × Zulip

OpenCode runs the agent and its tools; Zulip provides mobile and desktop chat, private channels and topic threads.

03

Fully self-hosted

Messaging, the bridge, the agent and your models all run on your hardware. You control every data flow.

04

The same session, not a copy

Each topic is bound to an existing OpenCode session. No copied history, no forks, no second backend pretending to continue.

05

Approvals from your phone

Permission requests and the agent's questions arrive in the topic. Answer with !ok 1234 or a button.

06

Your models and tools

Pick providers, models and variants from OpenCode's own catalog, with your existing MCP configuration.

Components

  • jt-oz-bridge serve — the bridge service: Zulip events in, authorization, OpenCode API calls, results out. Listens on loopback only.
  • Its own SQLite database (PostgreSQL in development) with application-level payload encryption. OpenCode's database is never opened.
  • An optional read-only local observer for jt-oz-bridge sessions and doctor.
  • Small read-only helpers, run as the OpenCode account, that prove which process, dataset and project directory are the real ones.
  • Optional units that post one notice to Zulip when the bridge stops and one when it is back.

One topic, one session

private channel "project-a"
├── login fix   → OpenCode session A
└── API tests   → OpenCode session B

Open a topic, pick an existing session you may use (or start a new one in an enrolled project) and type. Everyone in a channel reads its topics, so separate audiences need separate private channels.

A few commands

In a connected topic, plain text goes to the AI. Every command is ! and one word.

CommandPurpose
!ok / !noYes / no to what the bridge asked; !ok 1234 answers a permission request
!stop / !goStop everything here / continue what is paused
!statusCurrent state and queued messages
!new / !disconnectNew conversation / disconnect the topic (the session stays in OpenCode)
!model / !agentChange model / agent
!files / !file pathFind files / download one
!helpEverything else

Install, upgrade, uninstall

The bridge runs on Linux with systemd, next to an existing OpenCode server, as a dedicated non-root user. Each release lives in its own directory named after the wheel's SHA-256, with hash-locked dependencies and a CycloneDX SBOM.

Install

  1. Build the wheel, hashed requirements.txt and SBOM, or carry an offline bundle with the dependency wheels.
  2. Verify SHA256SUMS, install into a fresh venv with --require-hashes, check the SBOM.
  3. Configure, generate the key, migrate, install the systemd unit, check /readyz.
  4. Connect a Zulip bot and private channel, onboard one OpenCode project.
Install guide →

Upgrade

  1. Install the new release beside the running one.
  2. Stop the bridge, take a backup, migrate.
  3. Switch the drop-in, wait for /readyz, run smoke checks.
  4. Roll back by pointing at the previous release; after a schema change, fix forward or restore the backup.
Upgrade guide →

Uninstall

  1. Optionally take a final backup; keep the key separately.
  2. Stop and remove units, releases, state, configuration and the service user.
  3. Zulip and OpenCode keep their data; deactivate the bot yourself.
Uninstall guide →

Offline install in short

# connected machine
uv build --wheel --out-dir "$OUT"
uv export --frozen --no-dev --no-emit-project --no-header --format requirements-txt -o "$OUT/requirements.txt"
pip download --require-hashes --only-binary=:all: --python-version 3.13 --platform manylinux_2_28_x86_64 \
  -r "$OUT/requirements.txt" -d "$OUT/wheels"      # plus SBOM and SHA256SUMS

# air-gapped target
sha256sum -c SHA256SUMS
uv venv --offline --python "$PY" "$R/venv"
uv pip install --offline --no-index --find-links ./wheels --require-hashes -r requirements.txt --python "$R/venv/bin/python"
uv pip install --offline --no-index --no-deps jt_oz_bridge-*.whl --python "$R/venv/bin/python"

The guide has the complete commands, including the exact platform tags, carrying Python and uv, and the SBOM check.

Security model

  • Deny by default. Only configured Zulip users, private channels and per-project grants reach a session. Bot messages are ignored; model output cannot grant permissions.
  • Recheck before every effect. Source message, audience, grants, binding and the exact session are checked again; an operation with an unknown outcome is held, never resent blindly.
  • OpenCode stays authoritative and private. Loopback API only, never its database, never a restart. Its own tool, MCP and OS permissions still decide what the agent can do; bridge confirmations are not a sandbox.
  • Secrets by reference to owner-only files; the encryption key is kept apart from backups.
  • Files as files. Original bytes only; HTML is a download, never an interactive preview.
  • Hardened units and supply chain. Dedicated users, no capabilities, strict filesystem protection, hash-pinned dependencies and an SBOM for every release.
